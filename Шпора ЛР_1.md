## <mark style="background: #D2B3FFA6;">Создать таблицу</mark>

```sql
CREATE TABLE example (
    example_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    patient_id bigint NOT NULL,
    name text NOT NULL,
    quantity integer NOT NULL DEFAULT 1,
    CONSTRAINT example_patient_fk FOREIGN KEY (patient_id)
        REFERENCES patient (patient_id) ON DELETE RESTRICT,
    CONSTRAINT example_quantity_ck CHECK (quantity > 0),
    CONSTRAINT example_patient_name_uk UNIQUE (patient_id, name)
);
```

`CREATE TABLE` создаёт таблицу. В скобках пишу поля и ограничения. `IDENTITY` выдаёт id автоматически. `PRIMARY KEY` определяет строку; `FOREIGN KEY` ссылается на другую таблицу; `NOT NULL` требует значение; `DEFAULT` подставляет значение, если поле пропущено; `CHECK` проверяет условие; `UNIQUE` запрещает повтор. `ON DELETE RESTRICT` не даёт удалить **строку** пациента, если на неё ссылаются.

`example` — только пример. В моей настоящей схеме таблицы уже созданы в `schema.sql`; повторно запускать его в заполненной базе нельзя.

### <mark style="background: #D2B3FFA6;">Типы, которые я использую</mark>

| Тип | Для чего |
| --- | --- |
| `bigint`, `integer`, `smallint` | Целые числа разного диапазона |
| `text`, `varchar(20)` | Текст; у `varchar(20)` максимум 20 символов |
| `date` | Только дата, например день рождения |
| `timestamptz` | Дата и время с учётом часового пояса |
| `numeric(8,2)` | Точное число: всего до 8 цифр, 2 после запятой |
| `boolean` | `true` или `false` |

## <mark style="background: #D2B3FFA6;">Добавить и изменить строки</mark>

```sql
INSERT INTO specialty (name) VALUES ('Новая специальность');
```

`INSERT INTO` добавляет строку. Сначала перечисляю поля, после `VALUES` — значения в том же порядке. Если есть внешний ключ, сначала должна существовать строка, на которую я ссылаюсь.

```sql
UPDATE appointment
SET status = 'completed'
WHERE appointment_id = 5;
```

`UPDATE` меняет существующую строку, `SET` задаёт новое значение, `WHERE` выбирает нужную строку. **Без `WHERE` изменятся все строки таблицы.** Это образец: перед реальной правкой проверяю, какой именно приём нужно изменить.

```sql
DELETE FROM specialty WHERE specialty_id = 3;
```

`DELETE` удаляет выбранную строку. Если на неё ссылаются врачи, мой `ON DELETE RESTRICT` не даст удалить её. **Без `WHERE` команда попытается удалить все строки таблицы.**

## <mark style="background: #D2B3FFA6;">Прочитать данные и соединить таблицы</mark>

```sql
SELECT patient_id, full_name
FROM patient
WHERE medical_record_number = 'MR-0001'
ORDER BY full_name;
```

`WHERE` фильтрует строки, `ORDER BY` сортирует результат. `AS` даёт временное имя полю или таблице в конкретном запросе.

```sql
SELECT a.appointment_id, p.full_name AS patient
FROM appointment AS a
JOIN patient AS p ON p.patient_id = a.patient_id;
```

`JOIN ... ON` соединяет строки, для которых условие после `ON` совпало. Здесь приём соединяю с его пациентом по ключу. Обычный `JOIN` не показывает строку, если пары не нашлось.

```sql
SELECT a.appointment_id, dg.code AS diagnosis_code
FROM appointment AS a
LEFT JOIN appointment_diagnosis AS ad
    ON ad.appointment_id = a.appointment_id
LEFT JOIN diagnosis AS dg
    ON dg.diagnosis_id = ad.diagnosis_id;
```

`LEFT JOIN` сохраняет **все приёмы**, даже когда диагноза ещё нет. Тогда `diagnosis_code` будет `NULL`. Если на одном приёме два диагноза, приём появится в результате дважды — это строки результата, а не два одинаковых приёма в таблице.

```sql
SELECT COUNT(*) FROM appointment;
```

`COUNT(*)` считает строки. `UNION ALL` ставит результаты нескольких `SELECT` друг под другом. `IS NULL` ищет отсутствующее значение; писать `= NULL` нельзя.

## <mark style="background: #D2B3FFA6;">Изменить существующую структуру</mark>

Новая просьба преподавателя выполняется через `ALTER TABLE`, без пересоздания базы

```sql
ALTER TABLE doctor ADD COLUMN hire_date date;
```

Добавляет поле. Старые строки получат в нём `NULL`. Если поле должно стать обязательным, сначала заполняю старые строки **реальными данными из условия**, потом задаю `NOT NULL`:

```sql
UPDATE doctor SET hire_date = DATE '2020-01-01'
WHERE doctor_id = 1;

ALTER TABLE doctor ALTER COLUMN hire_date SET NOT NULL;
```

Последняя команда сработает, только если `NULL` не осталось ни у одного врача. Чтобы добавить правило:

```sql
ALTER TABLE doctor
ADD CONSTRAINT doctor_license_length_ck
CHECK (length(btrim(license_number)) >= 4);
```

Чтобы изменить старое правило, сначала выясняю его имя и влияние на данные. Синтаксис удаления ограничения: `ALTER TABLE doctor DROP CONSTRAINT doctor_license_length_ck;`. Без причины ограничения не удаляю.

## <mark style="background: #D2B3FFA6;">Индексы и составные ключи</mark>

```sql
CREATE INDEX doctor_specialty_idx ON doctor (specialty_id);
```

Обычный индекс помогает искать врачей по специальности. PostgreSQL сам создаёт индексы для `PRIMARY KEY` и `UNIQUE`, но не создаёт автоматически индекс на каждый внешний ключ.

```sql
CREATE UNIQUE INDEX appointment_one_primary_diagnosis_uk
ON appointment_diagnosis (appointment_id)
WHERE is_primary;
```

Уникальный индекс ещё и защищает правило: на один приём — **не более одного** основного диагноза. `WHERE is_primary` означает, что строки с `false` в этот индекс не входят.

Составной ключ `(appointment_id, diagnosis_id)` в `appointment_diagnosis` запрещает повтор **одной и той же пары**. Первый id отдельно повторяется, потому что на приёме может быть несколько диагнозов; второй отдельно повторяется, потому что диагноз может встречаться на разных приёмах.

## Транзакция и ошибки

```sql
BEGIN;
-- здесь команды изменения
COMMIT;
```

`BEGIN` начинает транзакцию, `COMMIT` сохраняет изменения. Если команда внутри неё упала, выполняю `ROLLBACK;`: изменения этой транзакции отменятся

## <mark style="background: #FF5582A6;">Нормальные Формы</mark>

**<mark style="background: #ADCCFFA6;">1НФ</mark>:** не запихиваю список в одну ячейку. У приёма два диагноза — значит, две строки в `appointment_diagnosis`, а не текст `'I10, Z00.0'` в `appointment`.

**<mark style="background: #BBFABBA6;">2НФ</mark>:** если ключ состоит из двух частей, свойство строки должно зависеть от **всей пары**. `is_primary` и `notes` описывают *этот диагноз на этом приёме*. Название диагноза зависит только от `diagnosis_id`, поэтому находится в `diagnosis`, а не в `appointment_diagnosis`.

**<mark style="background: #FFB8EBA6;">3НФ</mark>:** не дублирую в таблице сведения о другом объекте. `doctor` хранит `specialty_id`, а название специальности лежит в `specialty`. `appointment` хранит ссылки на пациента и врача, а не копии их ФИО. Если название специальности поменяется, исправлю одну строку.
